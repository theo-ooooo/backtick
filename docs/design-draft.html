React 서버 컴포넌트를 6개월 써보고 정리한 것들

SH
이수현 · 2026년 8월 6일 · 12분 읽기

RSC를 프로덕션에 넣기로 결정한 건 작년 12월이었다. 당시 우리 서비스의 초기 번들은 gzip 기준 412KB였고, 그중 절반 이상이 상세 페이지에서만 쓰이는 마크다운 렌더러와 하이라이터였다. 클라이언트로 내려보낼 이유가 없는 코드였다.

경계는 폴더가 아니라 데이터가 정한다

처음엔 app/ 아래를 기능별로 나누고 각 폴더 최상단에 "use client"를 붙였다. 편했지만 트리 전체가 클라이언트로 넘어갔다. 경계를 정하는 기준은 폴더 구조가 아니라 그 컴포넌트가 서버 데이터에 직접 의존하는지 여부여야 한다.

app/post/[slug]/page.tsx 복사 
export default async function Page({ params }: Props) {
  const post = await getPost(params.slug)   // 서버에서만 실행
  const html = await renderMarkdown(post.body)

  return (
    <article>
      <PostHeader post={post} />
      <div dangerouslySetInnerHTML={{ __html: html }} />
      <Comments postId={post.id} />   {/* 여기서만 "use client" */}
    </article>
  )
}

이렇게 바꾼 뒤 상세 페이지의 클라이언트 번들은 412KB에서 254KB로 줄었다. 마크다운 파이프라인 전체가 서버에 남았기 때문이다.

경계를 옮기는 작업은 리팩터링이 아니라 성능 예산을 다시 배분하는 일에 가깝다. 어디까지 서버에 둘지는 팀이 합의해야 한다.

워터폴은 조용히 생긴다

서버 컴포넌트 안에서 await를 순차로 쓰면 네트워크 탭에는 아무 흔적도 남지 않는다. 문제가 드러나는 건 TTFB뿐이다. 우리는 부모에서 필요한 데이터를 모두 병렬로 시작하고, 자식에는 프로미스를 내려보내는 방식으로 정리했다.
